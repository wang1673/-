## 基本情况

- 一句话：输入一段真实或生成的音乐和编辑文字，输出在改变指定属性后仍尽量保留原曲结构的高保真立体声音频；也能从文字直接生成音乐。
- 开源范围：公开的是 AudioCraft/MelodyFlow 推理与 demo 代码及预训练权重；训练代码未公开。专用实现位于 [facebook/MelodyFlow Hugging Face Space](https://huggingface.co/spaces/facebook/MelodyFlow)，不应误认为当前 AudioCraft GitHub 默认分支含有同一套独立 MelodyFlow 文件。代码 MIT；权重 CC-BY-NC 4.0（模型卡）。
- 和后续论文的关系：它先解决“音乐如何压成适合连续 flow 建模的 latent，并通过反演编辑”；后面的 FlowEdit 等工作针对直接编辑是否能绕开反演。

## ① 动机

### 先用一句话说它做什么

给模型一段现成音乐和一句修改要求，例如“把合成器低音改成 oud（乌德琴）低音，保留怀旧、充满活力的感觉”，模型需要改动音色与风格，同时尽量不毁掉原有节奏、旋律走向和整体情绪。MelodyFlow 让同一个模型也能从文字生成音乐；编辑时则把已有音乐先映到连续 latent，再沿生成模型学到的 ODE 路径反向走一段、换编辑文字向前生成。

### 以前卡在哪里

1. **专用编辑模型只会少数操作。** 过去常见方案各自处理人声移除、补全或旋律条件等特定任务，不容易把同一个编辑器用于换乐器、换流派、改录音环境等开放式要求。
2. **高保真立体声让离散 token 很贵。** 48 kHz 双声道波形本身很长。若用离散 codec，想保住细节通常要提高 token 帧率、词表或残差码本数量，生成模型也随之变重、变慢。
3. **只从噪声重新生成，原曲容易丢。** 文字生成模型知道目标风格，却没有原曲的具体节拍、配器和旋律；必须找到一条从原曲通往可编辑状态的路径，才能在改目标时留下足够多原有信息。
4. **朴素反演不够可逆。** Flow Matching 理论上用直线路径连接噪声与数据，但训练出的速度场和实际求解轨迹不会完全笔直；分类器自由引导还会让速度预测偏离训练分布。简单地把 ODE 倒着积分再正着积分，重建可能漂移，编辑也可能顾此失彼。

### 作者押注的关键想法

作者押注：如果先用低帧率、量化自由的连续 VAE codec 把 48 kHz 立体声压成平滑 latent，再让一个文本条件 DiT 学会从噪声到音乐 latent 的流，那么生成可以用较少 ODE 步完成；对真实音乐做编辑时，再把 ReNoise 的逐步校正思想改造成 flow 版本，反向轨迹会更适合编辑和重建。

### 具体场景

原曲描述是“怀旧、反思的电子另类音乐，带有充满活力的合成器低音”。编辑提示改成“怀旧、反思的中东另类音乐，带有 oud 低音，依然充满活力”。模型的目标不是重新写一首完全无关的中东音乐，而是把低音音色与风格往 oud / 中东方向推，同时保留原有音乐的活力和可辨认的组织。作者项目页列出了这类源描述和编辑提示的试听对照。

### 图 1 先看什么

[打开论文 PDF 第 3 页的图 1](https://arxiv.org/pdf/2407.03648#page=3)。图展示的是完整编辑闭环：真实波形先经 VAE 编码；上半部分用 DiT 和 ODE 反向估计中间 latent，并逐步做 regularization；到达编辑时间点后，下半部分换成目标文字，正向积分生成编辑后的 latent，最后由 VAE 解码回波形。接下来架构站会逐块拆图；本阶段先抓住动机：编辑器要有一条既能从原曲出发、又能朝新文字条件前进的连续路径。

**一句话回顾：** MelodyFlow 用低帧率连续音频 latent 降低高保真立体声生成成本，再用经正则化的反向 ODE 轨迹给零样本音乐编辑保留原曲依据。

**来源校准：** 上述问题动机与方法主张来自论文 §1–2；具体 oud 编辑场景来自作者项目页示例。论文实验结论和“现在的研究地位”留到第⑦站再讨论。


## ② 架构：连续 latent 上的文本条件流

### 先把图 1 读成一条管线

输入波形 → VAE codec 编成连续序列 (x_{src}) → 以源描述（或空文本）条件反向求解 ODE，得到中间态 (z_{T_{edit}}) → 以编辑提示为条件从 (T_{edit}) 正向求解 ODE → codec 解码成编辑波形。图中上半段负责“把原曲搬到可编辑位置”，下半段负责“带着原曲信息朝新文本生成”。[论文图 1（PDF 第 3 页）](https://arxiv.org/pdf/2407.03648#page=3)

### 三块核心组件

**1. 连续音频表示。** 论文 §2.1 的 codec 从 EnCodec 衍生，并吸收 DAC 的 Snake 激活和分频带 STFT 判别器，以及 KL 正则化瓶颈和感知加权。卷积 VAE 把高采样率波形压成低帧率连续 latent；medium 模型处理 48 kHz 立体声、25 帧/秒。它没有先把 latent 量化为离散 codebook token，因此后续 DiT 在连续向量序列上工作。

**2. 文本条件 Flow Matching DiT。** 训练时取音乐 latent (x) 和高斯噪声 ε，按
[
z_t=t x+(1-t)\epsilon,\qquad t\in[0,1]
]
构造中间态。线性路径的目标速度是
[
\frac{dz_t}{dt}=x-\epsilon=v_\theta(z_t,t,c).
]
DiT 接收当前 latent、flow 时间 (t) 和文本条件 (c)，用 T5 文本表征做 cross-attention，估计速度向量场。生成时从 (z_0=\epsilon) 开始，把这个场交给 ODE 求解器从 (t=0) 积到 (1)，得到 (z_1\approx x)，再经 VAE decoder 还原波形。

**3. 正则化反演编辑。** 对原曲编码得到 (x_{src}) 后，从 (t=1) 反向积分到 (T_{edit})，得到 (z_{T_{edit}})。再换目标文字 (c_{edit})，从 (T_{edit}) 向 (1) 积分。理想情况下，若目标文字仍是源描述，正向重建应近似还原输入；真实速度场受数值误差和 CFG 影响会漂移，因此作者逐步修正反演轨迹，并用 patch-KL 项约束预测速度的统计特征（§2.3–2.4）。

### 用小例子理解时间方向

设原曲 latent 是 (x_{src})，其描述是“轻快的合成器流行乐”，编辑提示是“轻快的合成器流行乐，加入木吉他”。先从 (t=1) 的原曲 latent 反向积分到 (T_{edit}=0.04)，过程中仍用源描述并做可逆性校正；随后在这个中间 latent 上改用新提示，正向走回 (t=1)。因为起点来自原曲而非纯噪声，模型有机会保留节奏、段落组织和主旋律走向，同时把音色推向木吉他。保留多少是连续权衡，不是逐轨隔离，因此不能保证只改一个乐器。

### 论文设置与代码默认值要分开读

论文 medium 模型报告 25 次反向步、每步 (K=4) 次可逆性估计、λKL=0.2；编辑 CFG 取 4.0。公开 wrapper 的默认编辑参数是 Euler 25 步、regularization 开启、4 次迭代、最后保留 2 次迭代、λ=0.2，默认 (T_{edit}=0.0)。因此复现实验应显式传入论文设置（论文主实验的 (T_{edit}) 与代码 API 默认值不同），不能仅依赖默认参数。细节见[代码树与论文对照](./代码树与论文对照.md)。

### 结构回顾

`MelodyFlow` wrapper 串接 codec 与连续 flow 模型；`FlowModel` 承担 DiT 速度预测、文本条件、CFG、ODE 正反向积分和反演正则化；codec 负责编解码。源码里变量名 `lm` 容易误导：此处核心生成器仍是连续 latent FlowModel，并非离散 token 的自回归语言模型。每个目录和论文小节的逐项映射见独立代码树说明。

**本阶段一句话：** MelodyFlow 把高保真音乐编辑变成“连续 latent 中的可条件 ODE 轨迹搬运”，反演端把原曲信息带到中间态，生成端再沿目标文本速度场前进。

**本阶段来源：** [论文 §2.1–2.4、图 1、§3.1–3.2](https://arxiv.org/pdf/2407.03648)；[官方推理实现 melodyflow.py](https://huggingface.co/spaces/facebook/MelodyFlow/blob/main/audiocraft/models/melodyflow.py)；[FlowModel 实现](https://huggingface.co/spaces/facebook/MelodyFlow/blob/9d0d223e9a63bbb8c20b9f57c5afcb4de297e6da/audiocraft/models/flow.py)。

**开源范围校准：** 本阶段校正基本信息中的“代码开源”：公开的是 AudioCraft/MelodyFlow 推理与 demo 代码及预训练权重；训练代码未公开。该专用实现位于 [facebook/MelodyFlow Hugging Face Space](https://huggingface.co/spaces/facebook/MelodyFlow)，不应误认为当前 AudioCraft GitHub 默认分支含有同一套独立 MelodyFlow 文件。代码 MIT；权重 CC-BY-NC 4.0。

## ③ 训练：学会从噪声指向音乐的速度

### Flow Matching 的训练样本怎么造

先从 codec 得到一段音乐 latent (x)，再从高斯分布采一个同形状噪声 (n\sim\mathcal N(0,I))。随机取 flow 时间 (t\in[0,1])，构造
[
z_t=t x+(1-t)n+10^{-5}\eta,
\]
其中极小的 (\eta\) 是实现讨论里提到的数值扰动。训练目标是
[
v^*=x-n,\qquad
\mathcal L_{FM}=\mathbb E_{x,n,t,c}\big[\|v_\theta(z_t,t,c)-(x-n)\|_2^2\big].
]
直观地说，模型每次看到一段“处在噪声和音乐之间”的 latent，必须预测沿这条线从噪声端走向音乐端的方向。(t=0) 是噪声端，(t=1) 是音乐端。论文 §2.2 给出目标速度和插值；作者在官方讨论中补充了实际训练采样写法与 MSE 目标。[论文](https://arxiv.org/pdf/2407.03648) · [作者训练细节答复](https://huggingface.co/spaces/facebook/MelodyFlow/discussions/2)

### 用标量例子验算

若某个 latent 维度的真实值 (x=2)、噪声 (n=-1)，取 (t=0.25)，那么中间点 (z_t=0.25(2)+0.75(-1)=-0.25)，目标速度 (x-n=3)。学到速度后，积分器从噪声端一路沿估计方向移动；实际音乐 latent 是高维序列，模型同时利用时间嵌入和文字条件预测每个位置的速度。

### 为什么要做 batch optimal transport 配对

若 batch 里的每个音乐 latent 随机配一个噪声，配对距离可能很大，训练路径会互相交叉、不够直。MelodyFlow 在每个 batch 内按 latent 与噪声之间的 L2 距离做线性指派，选择总配对代价较低的一组对应关系（Hungarian / linear assignment）。这叫 minibatch coupling。它不是编辑时的对齐，而是训练阶段为噪声与音乐样本选配对，令路径更接近模型假定的线性运输。消融表中依次加入 logit-normal 时间采样和 batch coupling 后，验证 MSE / 测试 FAD 均改善（论文表 4）。

### 两个模型阶段，两个目标

**Codec 先训练。** 论文附录报告：32 kHz 单声道、20 Hz，以及 48 kHz 立体声、25 Hz 两种 codec；latent bottleneck 维度 128。用 1 秒随机音频片段训练 200K 步，AdamW、学习率 3e-4，并包含多分辨率 STFT 重建、感知加权、VAE KL 瓶颈、分频带判别器和立体声 sum/difference loss。codec 训练完成后，逐维统计 latent，用于 flow 模型训练前的归一化。

**再训练 DiT 速度场。** 论文报告 T5 条件表征以 cross-attention 注入；训练时 20% 概率丢弃文字条件，让模型也能给出无条件预测，供推理时 CFG 使用。flow 时间采用 logit-normal 采样；移除了此前基线的 infilling objective，并采用 batch coupling。small 为 400M，240K 步；medium 为 1B，120K 步；两者 batch size 576、AdamW（β₁=0.9、β₂=0.95、weight decay=0.1）、梯度裁剪 0.2、cosine 学习率、4000 warmup steps；每 10 步更新一次 EMA（decay 0.99）。论文报告用 8 张 H100 96GB、bfloat16 与 FSDP 训练，small 约 3 天、medium 约 6 天。以上是论文附录的复现参数，不是开源训练脚本实际跑出来的日志。[附录 A.1](https://arxiv.org/pdf/2407.03648)

### 训练数据与可复现边界

论文 §3.3 报告内部 10K 首选音乐轨，以及 Shutterstock 25K、Pond5 365K 纯器乐曲目，总计约 20K 小时；元数据文字描述可能含流派、BPM、调性。官方模型说明页当前另写“16K hours”。两处口径不一致，笔记保留论文的逐项统计，并把差异注明；底层授权曲目和内部数据不能由公开材料重建。[论文数据段](https://arxiv.org/pdf/2407.03648) · [官方模型说明](https://huggingface.co/spaces/facebook/MelodyFlow/blob/main/docs/MELODYFLOW.md)

训练流程不能只靠公开推理仓库完整复现：作者在官方讨论明确表示不计划发布训练代码。公开实现可用于推理和检查网络前向；训练损失、超参、样本配对等细节来自论文附录和作者答复。作者答复建议微调时按速度预测任务做，但这不是完整可运行的官方 finetuning recipe。

**本阶段一句话：** codec 学会把波形压成可建模的连续空间；DiT 学会在任意 flow 时间预测“从噪声到音乐”的速度，而 logit-normal 时间采样、CFG 条件丢弃和 batch OT 配对让训练路径更适配快速 ODE 生成。

**本阶段来源：** [论文 §2.1–2.2、§3.3、附录 A.1、表 4](https://arxiv.org/pdf/2407.03648)；[作者公开训练细节答复](https://huggingface.co/spaces/facebook/MelodyFlow/discussions/2)。

## ④ 数据：长曲库如何变成短片段与评测集

### 训练集披露到什么程度

论文 §3.3 报告三部分音乐：内部高质量曲目 10K 首、Shutterstock 25K 首、Pond5 365K 首，合计约 20K 小时。训练曲目为 48 kHz 立体声，带文字描述，描述有时包含流派、BPM、调性；作者会清理与音乐无关的重复文本模式（例如 URL）。small 版输入先降到 32 kHz 单声道（双声道取平均），medium 用 48 kHz 立体声。官方模型说明页则写训练数据为 16K 小时，和论文的“20K 小时”不一致；两者都保留为来源原文口径，现有公开信息无法确定是统计口径变化还是文字未同步。[论文 §3.3](https://arxiv.org/pdf/2407.03648) · [官方模型说明](https://huggingface.co/spaces/facebook/MelodyFlow/blob/main/docs/MELODYFLOW.md)

### 长曲进入模型的方式

数据单位要分清三层：曲库中是 full-length 音乐；codec 训练用随机 1 秒片段；flow DiT 则在编码后的定长序列上训练。small 使用 32 kHz mono、10 秒片段、20 Hz latent（约 200 个时间帧）；medium 使用 48 kHz stereo、30 秒片段、25 Hz latent（约 750 帧）。codec latent bottleneck 维度为 128。模型不是对一整首数分钟歌曲一次性建模。

论文用 L-shaped attention mask 帮助 30 秒模型处理更短时长：每条序列随机抽一个边界，边界前的 token 只看自身，边界后的 token 可看整段上下文。它是在完整训练长度上模拟短片段能力，作者称可让短于 30 秒的推理更省算；这不意味着能直接泛化到超过 30 秒的歌曲，论文建议更长音频采用滑窗或 outpainting。

### 训练、验证和测试分别用什么

- **训练语料：** 上述内部与授权来源曲库；源音频及其商业许可数据本身没有随推理仓库公开。
- **生成评测：** MusicCaps 用于主文 text-to-music 结果；主观生成评测取 genre-balanced 集中的 198 个样本。
- **域内消融与编辑：** 单独留出的 8,377 首域内曲目用于消融和客观编辑评测；181 首高保真样本用于主观编辑评测。编辑提示先由 Llama-3 大模型按目标流派改写，再人工检查合理性与连贯性。
- **采样率和度量：** 客观指标计算前把立体声下混为单声道；主观试听保留原音频格式，样本统一响度至 -14 dB LUFS。

因此，“MusicCaps 指标”与“8,377 首域内编辑集”是不同实验设置；跨表比较时要看清数据集和样本筛选，不能把客观生成、编辑和主观打分当成同一批音频。

| Flow-small | 10 秒片段，32 kHz mono，20 Hz | 约 200 帧 latent；面向短音频生成 |
| Flow-medium | 30 秒片段，48 kHz stereo，25 Hz | 约 750 帧 latent；面向高保真立体声 |
| 生成测试 | MusicCaps；主观子集 198 条 | 文本生成评测，不等于域内编辑测试集 |
| 编辑测试 | 域内留出 8,377 首；主观子集 181 首 | 客观指标在域内集；人工打分在筛选后的高保真子集 |

**本阶段一句话：** MelodyFlow 从有文字描述的长曲库出发，先以短 crop 训练 codec，再用固定长度 latent 训练生成器；数据统计和不同测试集的口径决定了哪些实验能公平复现、哪些只能参考论文报告。

**复现边界：** 论文给出了曲目数量、小时数、采样率、切片长度和测试集规模，但没有发布原始授权音频、内部曲目、逐样本划分清单或完整训练代码。当前官方文档与论文训练时长统计还不一致，因此即使按公开超参数重写训练流程，也无法复原相同的数据抽样和评测切分。

**本阶段来源：** [论文 §3.1–3.4、附录 A.1.1–A.1.3、A.2.2](https://arxiv.org/pdf/2407.03648)；[官方模型说明](https://huggingface.co/spaces/facebook/MelodyFlow/blob/main/docs/MELODYFLOW.md)。

## ⑤ 信息流：从源音频到编辑音频逐步追踪

这一站把图 1 翻译成一次具体调用。设输入是“轻快的合成器流行乐”，目标是“轻快的合成器流行乐，加入木吉他”。公开实现将波形变为连续 latent，保留时间序列作为编辑起点；后续数值运算在这个潜空间中进行。

### 一次 edit 调用的 6 个节点

1. **载入模型。** `MelodyFlow.get_pretrained()` 由 loader 分别载入 compression model 和 Flow DiT。wrapper 在这里负责拼装组件、设定生成/编辑参数。
2. **音频编码。** `encode_audio(waveform)` 调用 codec encoder。VAE 会输出后验参数；推理路径从中采样 latent，并按训练时记录的均值、标准差标准化。原音频因此从波形空间变成模型训练使用的 latent 空间。
3. **准备两种文字条件。** `edit()` 将 `src_descriptions` 做成反演条件；若调用者没提供，就用空文本。目标 `descriptions` 独立做成生成条件。空文本代表无条件预测，不等于把目标提示留空。
4. **反演：从 (t=1) 走向 (T_{edit})。** wrapper 调用 `_generate_tokens`，给 `FlowModel.generate` 传入源 latent、`source_flowstep=1.0` 和 `target_flowstep=T_{edit}`。代码检测方向为反向后把 CFG 设为 0，以免引导使反演发散；每一时间步用 Euler 更新，开启 regularization 时用构造的参考 latent 与 patch-KL 速度校正。输出 intermediate latent。
5. **编辑生成：从 (T_{edit}) 回到 (1)。** wrapper 将中间 latent 作为 prompt，传入目标文字条件，再调用一次 `_generate_tokens`，这次方向是正向。DiT 预测速度场，CFG 对条件/无条件输出做组合，ODE 逐步更新 latent 到数据端。
6. **反标准化与解码。** `generate_audio(final_tokens)` 把 flow 输出按 latent 的均值、标准差反标准化，再调用 codec decoder 生成波形。用户得到的才是可试听音频。

### 一条精简的调用链

```text
MelodyFlow.get_pretrained
  ├─ load_compression_model
  └─ load_dit_model_melodyflow
edit(waveform latent, source text, target text)
  ├─ _prepare_tokens_and_attributes(source)
  ├─ _prepare_tokens_and_attributes(target)
  ├─ _generate_tokens(source condition, 1.0 → T_edit)
  │    └─ FlowModel.generate → forward/velocity → Euler + regularization
  ├─ _generate_tokens(target condition, T_edit → 1.0)
  │    └─ FlowModel.generate → conditional/unconditional CFG → ODE update
  └─ generate_audio → latent unnormalize → compression_model.decode
```

### 几个容易忽略的实现细节

- 如果 `src_descriptions` 不传，代码会以空描述做反演；给出源描述可能提高文字贴合，但反演核心仍是源音频 latent。
- 反演和重生成分成两个 `FlowModel.generate` 调用，源描述只进入第一个，编辑文本只进入第二个。
- 代码把条件与 null 条件合并成 batch 计算 CFG，减少重复 forward；反演方向则用 CFG=0。
- 该版本 FlowModel 对 regularized inversion 强制使用 Euler；midpoint 不支持 latent regularization。这解释了论文中“普通生成用 midpoint”和“编辑反演需逐步校正”不是冲突，而是不同计算段/能力约束。
- decoder 输出的波形质量仍受 codec 重建误差影响；flow 模型不能恢复 codec 已丢失的细节。

### 与论文图 1 的对应关系

| 论文图中的节点 | wrapper / 模块 | 张量含义 |
|---|---|---|
| VAE encoder，(x_{src}) | `encode_audio` → compression model | 源波形的后验 latent 采样并标准化 |
| 上半部反向 ODE | `edit` 第一次 `_generate_tokens` → `FlowModel.generate` | (t=1\to T_{edit})，空文本或源文本条件，CFG=0 |
| Regularize | `FlowModel.generate` 的反演循环 → `noise_regularization` | 参考路径预测和当前速度对齐，缓和累计漂移 |
| (z_{T_{edit}}) 中间态 | 第一次调用返回的 `intermediate_tokens` | 同时承接源音频结构和下一段编辑的起点 |
| 下半部正向 ODE | 第二次 `_generate_tokens` → `FlowModel.generate` | (T_{edit}\to1)，以目标文本条件更新 |
| VAE decoder，编辑波形 | `generate_audio` → compression model decoder | latent 反标准化后还原音频 |

**本阶段一句话：** wrapper 负责分配源条件与目标条件；FlowModel 负责 ODE 方向和每一步速度更新；codec 负责音频和连续 latent 的双向转换。

**本阶段来源：** [论文图 1、§2.3–2.4](https://arxiv.org/pdf/2407.03648)；[MelodyFlow wrapper](https://huggingface.co/spaces/facebook/MelodyFlow/blob/main/audiocraft/models/melodyflow.py)；[FlowModel 源码快照](https://huggingface.co/spaces/facebook/MelodyFlow/blob/9d0d223e9a63bbb8c20b9f57c5afcb4de297e6da/audiocraft/models/flow.py)。

## ⑥ 例子：indie-folk 到印度古典风格

论文附录 A.1.3 给出用于编辑提示设计的一个真实例子。原描述是：

> This is a lush indie-folk song featuring soaring harmony interplay and haunting reverb-y harmonica.

Llama-3 按“流派互换”方向提出目标描述，研究者再人工检查其合理性与连贯性：

> This is a lush Indian classical-inspired song featuring soaring harmony interplay and haunting reverb-y bansuri flute.

### 把每个短语放回信息流

| 提示片段 | 编辑意图 | 编辑时可能发生什么 |
|---|---|---|
| lush indie-folk → lush Indian classical-inspired | 将整体风格推向印度古典灵感 | 目标条件改变 forward ODE 的速度场，整体配器/音色可能随之重组 |
| harmonica → bansuri flute | 改变显著的主奏音色 | 模型更倾向生成 bansuri 长笛音色，但不是独立音轨替换，其他声部也可能一起变化 |
| soaring harmony interplay | 在源与目标描述里都保留的内容 | 给模型一个继续保留和声互动的文本线索 |
| haunting / lush | 两边都保留的情绪/质感 | 限定改变方向，避免提示只留下“印度古典”这一粗略风格标签 |

源音频编码成 (x_{src}) 后，反演可以使用源描述或空描述；到中间态后，生成段使用上面的目标描述。若反演文字条件使用源描述，模型先尽量把源音频和源描述纳入相同轨迹；若用空描述，就少依赖源文字而主要依靠源 latent。两种设定都不等于模型把 harmonica 轨道单独抽出来。

### 这个例子教我们怎样写编辑文本

MelodyFlow 论文特别说明：它接收的是“编辑后样本应该听起来怎样”的描述，而不是需要理解动作的指令。所以上例写成完整目标音景，列出希望改变的流派/乐器，并重复希望保留的氛围与和声；不是写成“把 A 乐器替换成 B 乐器”。后者要求模型理解明确的对象定位和局部编辑操作，论文并不声称模型具备这种指令解析能力。

做实验时可以把这个例子整理成三类观察：

1. **变化轴：** 流派与主奏乐器都变化，目标不是严格的单变量因果实验。
2. **保持线索：** lush、haunting、soaring harmony 在两条描述中重复，给模型保留整体氛围/和声互动的目标线索。
3. **比较准则：** 听编辑结果时分别评估新风格是否可辨、目标乐器是否出现、原有和声互动是否仍可感知、音质是否受损。主观上要分开“文本贴合”与“源曲一致”，两者可能此消彼长。

### 如何避免把文字示例误当成效果证据

该例只证明作者如何构造并人工校验测试 prompt；它本身不是某一条生成音频的定量结果，也不能证明所有输入都能把指定乐器精确替换。论文讨论承认文本编辑任务是开放式描述，特定编辑轴仍需要更准确的评价。配套样例音频可以在[作者项目页](https://melodyflow.github.io/)试听；评测结论和限制放到下一站 ⑦。

**本阶段一句话：** 把请求写成目标音景，并明确写出需要保留的属性；MelodyFlow 沿目标描述引导整段 latent 变化，不执行有保证的逐轨乐器替换。

**本阶段来源：** [论文附录 A.1.3 例子](https://arxiv.org/pdf/2407.03648)；[论文讨论中的指令限制](https://arxiv.org/pdf/2407.03648#page=10)；[作者项目页与试听样例](https://melodyflow.github.io/)。

## ⑦ 实验：质量、文本贴合、保真与速度

### 先看编辑主结果

编辑主观评测用 181 首域内高保真源音频，由听众按 1–5 分评价总体质量 OVL、与目标文本的相关性 REL、和原曲的一致性 CON。MelodyFlow-medium 得分分别为 **2.72±0.08、2.72±0.07、2.61±0.10**，三项平均 2.68；MusicGen-melody 为 2.57、2.46、2.14（均值 2.39）；AudioLDM 2-music 为 2.48、2.36、2.72（均值 2.52）。MelodyFlow 在质量和文本贴合最高，AudioLDM 2 的一致性更高。结果说明三项目标有张力：编辑器若过分贴着源音频，可能没有充分响应编辑提示；若重生成过多，又会降低原曲一致性。[论文表 1](https://arxiv.org/pdf/2407.03648)

### 哪些设计带来提升

- **反演比朴素 DDIM 更稳。** 在编辑指标 FADedit、CLAPedit 和 LPAPS 上，论文报告 MelodyFlow 与 ReNoise 均明显优于 DDIM；MelodyFlow 直接正则化速度预测时整体质量较好，反演 CFG=0、重生成 CFG=4。
- **原描述条件是取舍旋钮。** 反演时加入原曲描述会提高 CLAPedit（目标文字贴合），但也提高 FADedit（编辑样本分布偏离），所以“源信息更多”并不保证各指标一起变好。
- **codec 的 KL 瓶颈更均衡。** 表 3 消融表明：不正则 codec 的重建指标最好，但 KL codec 的生成 FAD 更好；20 Hz KL codec 与 50 Hz 版本相比大幅压低帧率而仍保持相近生成 FAD，因此用于 small。medium 为 48 kHz stereo 选 25 Hz。
- **Flow 设计逐项增益。** 表 4 的域内 FAD 从基线 0.53，移除 infilling 到 0.50，换 logit-normal 时间采样到 0.44，加 batch coupling 到 0.42，扩大模型后到 0.39。由于 infilling 任务更容易，基线 MSE 不可直接公平比较；FAD 趋势更适合看这些消融。
- **编辑速度要看总 NFE。** NFE 是 DiT 前向次数，含反演和重生成。论文图 4 的质量/速度折中甜点约在 128 NFE；作者指出自家反演在 125 NFE 才稳定超过 DDIM，而 DDIM 在 32 NFE 已能达到可接受 FAD。因此 MelodyFlow 的贡献是更好的编辑质量折中，不是每个预算下都更快。
- **生成的效率结果有任务边界。** MusicCaps 文本生成表里，small 64 步约 1.8 秒、medium 64 步约 2.3 秒（论文实验环境）；作者对照的 MusicGen-medium 为 1500 步、41.3 秒。论文附录还报告，在特定 FAD 对照中，MelodyFlow 16 NFE 得到 0.50，而重训基线要 256 NFE 才到 0.53。硬件、实现和模型版本会影响绝对时延。

### 如何读这些指标

- **FAD / FADedit 越低越好：** 生成样本分布是否接近参考音频分布；不是逐样本保真度。
- **CLAP / CLAPedit 越高越好：** 音频与描述的语义相似度；不能证明乐器局部编辑精确。
- **LPAPS 越低越好：** 原始与编辑 latent 的平均距离，作为源一致性的代理；太低也可能意味着编辑不充分。
- **OVL、REL、CON 越高越好：** 人类分别判断总体质量、目标文本相关性、与源曲一致性。它们比单一自动指标更贴近听感，但评测仍依赖有限样本和听众。

### 结论与限制

MelodyFlow 的证据链支持“低帧率连续 codec + Flow Matching DiT + 正则化反演”能在免微调音乐编辑中改善文本贴合与质量，并在约 125 NFE 的设置下取得有竞争力的源一致性。它在文本生成上与 MusicGen 大致相当，论文明确没有声称胜过当时所有顶尖生成系统；对照表中 Stable Audio 的人类偏好更高。

论文自身也指出：输入应是描述编辑后音频的文本，不是“把 A 乐器换成 B”这样的操作指令；虽然报告流派、乐器、速度、调性、补全等方向的有希望案例，针对每个编辑轴还缺少严格的定量评测。MusicCaps 上优化 FAD 可能通过过拟合训练集实现，且会和人类感知质量负相关。固定 (T_{edit}) 也没有覆盖创作者对“变化幅度—原曲保留”的不同偏好。超过训练 30 秒的长度需要滑窗或 outpainting。

**精读结论：** MelodyFlow 的关键贡献在反演轨迹与连续低帧率表示，而不是无条件地保证音乐某一声部被精确替换。它用额外的反向计算换取更稳的源结构保留；最终编辑强度仍需在一致性、文本贴合和质量之间选取。
